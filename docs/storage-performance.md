# Vec 存储与性能

四个算法共用同一存储实现。主引擎和 parcel_selectors 适配器不再使用自建哈希表。
主 crate 已移除直接的 rustc-hash 依赖。第三方依赖仍可能使用哈希表或 rustc-hash。
输入 JSON 的 Node.attributes 和 Node.extra 保留原有 HashMap 接口，属性进入引擎时转换成 Vec。
结果集合导出仍使用 BTreeMap 排序。

| 数据 | 当前表示 | 查询成本 | 新增成本 |
|---|---|---|---|
| 内部节点 | Vec<Option<DomNode>>，按实例 ID 减去起始 ID 寻址 | O(1) | 摊销 O(1) |
| 外部 trace ID | 按 u64 键排序的 Vec，值为可选内部 ID | O(log T) | 新键最坏 O(T) |
| 类名与属性名 | 稳定整数 ID，加按名称排序的 Vec 索引 | 输入名称二分查找 O(log N) 次字符串比较 | 新名称最坏移动 O(N) 个 ID |
| 节点类集合 | 排序且去重的 Vec<名称 ID> | O(log C) | 每次修改重新编码并排序 |
| 节点属性 | 按名称 ID 排序的稀疏 Vec<(ID, String)> | O(log A)，值比较另计 | 最坏 O(A) |
| 动态伪类 | u8 位掩码 | O(1) | O(1) |

T 表示上次 DOM 清空以来登记的不同外部 ID 数。N 表示引擎登记的不同名称数。
C 和 A 分别表示单个节点的类数量及属性数量。
外部 ID 不直接用作 Vec 下标。因此，稀疏 ID 或 u64::MAX 不会造成按最大 ID 分配内存。
外部 ID 删除只清空值，保留排序槽位。内部节点删除也保留空槽位，直到 DOM 清空。
名称 ID 跨 DOM 重新初始化保持有效。名称表随不同名称的累计数量增长，直到引擎释放。

Engine::new 把选择器中的类名和属性名编成整数条件。匹配阶段查找整数 ID。
输入仍可包含此前未出现的名称。每次 DOM 修改时在线编码，不预读未来 trace。
属性值保留原文。例如，class 集合去重不会改变 `[class="b a a"]` 的比较结果。
标签、HTML id 和属性值仍使用字符串比较。它们不是哈希表。
parcel_selectors 接收字符串查询。适配器直接扫描节点的类或属性 Vec，并按 ID 读取名称文本。
这一路径不反复搜索全局名称表。扫描和文本比较计入适配器耗时。

## 当前测量

三个基准均使用当前源码、release 构建和 CPU 4。每个实现预热一次，记录七次样本，并轮换执行顺序。

| 基准 | 数据 | 计时范围 | 校验 |
|---|---|---|---|
| [parcel_selectors 对比](benchmark.md) | 13 个数据集 | 分开测初始化与完整 trace，不计结果导出 | 每帧的完整匹配集合 |
| [网站数据对比](website-benchmark.md) | 11 个网站捕获数据 | 初始化后的更新与全节点 RGBA 输出 | 每帧完整 RGBA，另检查选择器投影 |
| [受控 Stylo 对比](stylo-benchmark.md) | 8 组受控用例 | 初始化后的 100 次更新与全节点 RGBA 输出 | 每帧完整 RGBA |

Engine::new 的选择器名称编码属于准备阶段，不计时。DOM 构造中的名称编码计入初始化。
修改时出现的新名称在线编码，计入更新耗时。测试不预读未来 trace 来分配 ID。
网站和受控基准排除初始化，不能用它们的更新数字推断启动成本。
新名称和新外部 ID 的插入有线性移动成本。表中的 Vec 查询并非全部 O(1)。

伪类刷新频率、dirty 遍历和四个缓存算法保持原流程。
全节点颜色输出仍需读取匹配位、选择获胜规则并排序。存储转换不会减少要求输出的节点数量。

旧版本也做了重测，但未修改的 Stylo 对照在不同批次间出现明显耗时变化。
因此，本报告不发布跨批次的 Vec 加速比。当前图表只比较同轮测量的实现。
CPU 调速模式不等于固定频率，CPU 亲和性也不等于隔离后台负载。
图中的样本范围用于显示波动，不是置信区间。接近的中位数不能直接说明性能优劣。

旧 Blink 测量的输出要求不同，相关报告已移除。
旧存储实验及重复图表也已移除，历史版本可从 Git 查询。

## 验证与证明边界

Rust 测试覆盖稀疏大 ID、重复类名、属性原文、新名称、重新初始化和删除。
语料回归检查覆盖 13 个数据集，比较 naive 与四个算法的最终匹配结果。
parcel_selectors 基准还检查这 13 个数据集的每帧匹配结果。
算法 Lean 证明及现有 Rust 源码证明均通过构建和公理检查。
源码证明使用 NodeArena 和 TraceIndex 的接口契约。
具体 Vec 存储、排序不变量及名称编码没有形式化精化证明。
详细边界见[源码证明说明](../formal/rust/README.md)。
